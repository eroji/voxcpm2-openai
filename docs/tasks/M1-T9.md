# M1-T9 — StreamingSpeech ownership + cancellation hardening (wave-3 review)

- **Milestone:** M1
- **Wave:** 4
- **owns:** `app/engine.py`, `app/speech.py`, `tests/test_speech.py`, `tests/test_stream_lifecycle.py`
- **deps:** M1-T7
- **verify:** `.venv/bin/python -m pytest tests/test_speech.py tests/test_stream_lifecycle.py -q && .venv/bin/ruff check app/engine.py app/speech.py tests/test_speech.py tests/test_stream_lifecycle.py`
- **requirements:** R-007, R-016, R-043

## Context

Wave-3 review proved the last slot leaks:

1. `StreamingSpeech` owns an engine slot, but `aclose()` only runs if its async generator is
   *started*. `await service.stream(...)` followed by dropping the object (or closing `chunks` before
   the first pull) leaves `_sem` at 0 forever for `pcm`, `wav` **and** `mp3/opus/flac` (the last also
   leaks ffmpeg). One such event per concurrency slot ⇒ permanent 429s.
2. `ffmpeg_stream` catches `Exception`; a `CancelledError` during `create_subprocess_exec` leaks the
   handle (same class).
3. `_resolve_adhoc` base64-decodes an unbounded `ref_audio` data URI (SPEC §10 upload cap spirit).
4. `ENGINE_SAMPLE_RATE` is duplicated in `speech.py` and `engine.py` (`_SAMPLE_RATE`).
5. `tests/test_stream_lifecycle.py::test_transport_error_mid_body` is flaky under the suite because
   the raw truncating server sends keep-alive; httpx reuses the health-check connection and the read
   error happens at `open_stream`, not mid-body.

## Steps

1. `app/engine.py`: rename `_SAMPLE_RATE` → public `ENGINE_SAMPLE_RATE = 48_000`; keep behavior.
2. `app/speech.py`:
   - Add `aclose: Callable[[], Awaitable[None]]` to `StreamingSpeech` (dataclass). Every branch must
     set it so cleanup works **without iterating**:
     - `pcm` passthrough: `handle.aclose`;
     - `wav`: a wrapper that closes the native generator **and** the handle;
     - ffmpeg: a wrapper that terminates the process, cancels the feeder, closes stderr/stdout and
       calls `handle.aclose()`; idempotent.
   - `SpeechService.stream` must not rely on generator start-up for ownership. Build the ffmpeg
     process eagerly (inside the try) or keep a `pump` coroutine whose cleanup function is stored in
     `aclose`; a second `aclose()` is a no-op.
   - `ffmpeg_stream`: on spawn/pipe failure use `except BaseException` → `await handle.aclose()`
     (through the owner), re-raise `CancelledError` unchanged; map real errors to `EngineError`.
   - `_resolve_adhoc`: reject `len(ref_audio) > (settings.max_upload_bytes * 4 // 3) + 256` with
     `BadRequest(code="ref_audio_too_large")` before decoding.
   - Use `ENGINE_SAMPLE_RATE` for the passthrough comparison, ffmpeg input rate and WAV header.
3. Tests:
   - Never-iterated: for each of `pcm`, `wav`, `mp3`, `speech = await service.stream(...)`,
     `await speech.chunks.aclose()` (without pulling), then `service.synthesize(...)` succeeds
     (`concurrency=1, max_queue=0`).
   - `await speech.aclose()` also releases; calling it twice is safe.
   - Cancel during ffmpeg spawn: monkeypatch `asyncio.create_subprocess_exec` with a coroutine that
     sleeps, cancel `service.stream(...)`/the task, assert a follow-up `synthesize` succeeds.
   - Oversized `ref_audio` (limit monkeypatched small) → 400 `ref_audio_too_large`.
   - `settings.sample_rate=24000`: streaming `pcm` output is resampled (X-Sample-Rate 24000, output
     is 24 kHz s16le) while the engine input is still 48 kHz.
   - Fix the flaky test: add `Connection: close` to the truncating server's responses (and/or a
     dedicated client with `max_keepalive_connections=0`) so the failure is deterministic mid-body.
4. Do not edit routers, store or fixtures.
