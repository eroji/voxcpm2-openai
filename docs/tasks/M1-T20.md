# M1-T20 — Normalize engine streaming format/rate (fix garbled stream)

- **Milestone:** M1
- **Wave:** 19
- **owns:** `app/engine.py`, `app/speech.py`, `tests/fake_engine.py`, `tests/test_engine.py`, `tests/test_stream_lifecycle.py`, `tests/test_speech.py`, `tests/test_streaming.py`
- **deps:** M1-T9
- **verify:** `.venv/bin/python -m pytest tests/test_engine.py tests/test_stream_lifecycle.py tests/test_speech.py tests/test_streaming.py -q && .venv/bin/ruff check app/engine.py app/speech.py tests/test_engine.py tests/test_stream_lifecycle.py tests/test_speech.py tests/test_streaming.py`
- **requirements:** R-016, S3; reported bug: streamed `/api/speak` is garbled while non-streamed is fine

## Context

The non-streamed path decodes the engine WAV and knows its real sample type/rate; the streamed path
assumes s16le @ 48 kHz. If the engine streams float32, another rate, or another channel layout, the
browser gets noise. Make the app ask the engine for `response_format=wav` on stream requests, parse
the WAV header once, strip it, convert float32→s16le if needed, and expose the actual sample rate so
the app can resample to the requested output rate.

## Steps

1. `app/engine.py`:
   - `StreamHandle` gains `sample_rate: int` (and `chunks` remains s16le mono).
   - For streaming requests force `response_format="wav"` in the POST body (the caller's `fmt`
     remains pcm/wav for downstream semantics).
   - `_stream`: buffer until the first 44+ bytes; if it starts with `RIFF`/`WAVE`, parse
     `fmt ` (`audio_format`, channels, rate, bits) with `struct`, strip the header, and convert:
     - PCM 16-bit → pass through;
     - IEEE float 32-bit → `pcm_s16le(np.frombuffer(..., "<f4"))`;
     - anything else → `EngineError("unsupported engine stream format ...")`.
     Keep 2/4-byte carry across chunks. If no RIFF header arrives (engine ignores wav), fall back to
     s16le @ 48000 and log once.
   - Record metrics/first-audio after the header is stripped.
2. `app/speech.py`:
   - `SpeechService.stream`: `source_rate = handle.sample_rate`; passthrough only when
     `fmt == "pcm"` **and** `target_rate == source_rate`; otherwise `ffmpeg_stream(source,
     source_rate, target_rate, fmt)`; `_wav_native` uses `target_rate`. `X-Sample-Rate` stays the
     target rate.
   - Ensure `/api/speak` take saving decodes the WAV stream (`decode_any`) and resamples to 48 kHz
     (already does when `is_pcm` is false — confirm the new stream format makes that path the one
     used).
3. `tests/fake_engine.py`: stream responses honor `response_format`:
   - `wav` → 44-byte PCM16 header + 10 chunks; `pcm` → raw s16le as today;
   - add an optional `state["stream_format"]` (`"wav16"` default, `"wav_f32"`, `"pcm16"`) and
     `state["stream_rate"]` (default 48000) so tests can cover float32/24 kHz.
4. Tests:
   - `EngineClient.open_stream` on the default fake: no RIFF bytes in chunks, `sample_rate==48000`,
     decoded duration ~0.6 s.
   - `wav_f32`: same audio duration after conversion, no NaN/static (assert peak in 0..1 and
     finite).
   - `stream_rate=24000`: handle sample rate 24000; `SpeechService.stream` with target 48000
     produces 48 kHz output (X-Sample-Rate 48000, ffmpeg path); with target 24000 pcm passes
     through.
   - Raw `pcm16` fallback still yields 48000.
   - Existing stream lifecycle/queue tests stay green.
5. Do not edit UI or container files.

**Deviations**

1. The header is read/stripped inside `open_stream` (before it returns), not lazily inside the
   chunk generator: `SpeechService.stream` needs `handle.sample_rate` to pick passthrough vs
   ffmpeg. Side effect — a malformed/unsupported engine container now raises `EngineError` (502)
   *before* the router sends headers instead of streaming noise, and the slot is released there
   (covered by `test_stream_unsupported_sample_format`).
2. `state["stream_format"]` defaults to `None` = "follow the request's `response_format`" (which
   resolves to `wav16` for every stream the app makes) rather than the literal `"wav16"`, so the
   fake still satisfies "pcm → raw s16le as today" for direct callers.
3. Beyond the brief's list, inside `app/engine.py`: the header parse walks chunks (so a leading
   `LIST` or a 40-byte `fmt ` can't desync it), resolves the `WAVE_FORMAT_EXTENSIBLE` sub-format
   tag, and downmixes multi-channel streams to mono. All are ≤5 lines each; without them a real
   engine header that is not the minimal 44-byte layout would garble again.

**Assumptions / open questions**

- S3 is unverified here: the real engine's streamed WAV is assumed to be PCM16 or IEEE-float32
  mono with a standard `fmt `/`data` layout. Anything else is now a loud 502 instead of static,
  and a header-less stream keeps the SPEC §6 documented fallback (s16le @ 48 kHz, logged once).
- `/api/speak` take saving needed no change: `response_format` is still `pcm`/`wav` downstream, so
  the `decode_any` branch is the one used for `wav` streams (now asserted by
  `tests/test_streaming.py`).
